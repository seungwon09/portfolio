# 앱 개발의 아이디어와 의사결정 과정

> KITA · Timora · Jarvis

KITA는 학생이 문제의 정답을 확인하는 데서 그치지 않고 시험에서 더 빠르고 정확하게 풀도록 돕기 위해 만들었습니다. Timora에서는 공부 시간과 계획을 계정에 저장하고 여러 기기에서 이어 쓰는 학습관리 앱을 개발했습니다. Jarvis에서는 여러 AI와 컴퓨터 기능을 하나의 명령으로 연결하는 개인비서로 범위를 넓혔습니다.

실제 코드 작성과 여러 파일의 수정은 주로 Codex가 담당했습니다. 저는 서비스의 목적과 사용 기준을 정하고, AI의 제안을 이해한 뒤 선택하거나 바꾸며, 실행 결과에 따라 다시 수정했습니다.

처음부터 서버와 데이터베이스, 보안을 모두 알고 시작한 것은 아닙니다. 모르는 부분은 AI에게 질문했고 설명을 들으며 개발을 이어갔습니다. 다만 화면이 만들어졌거나 AI가 완료했다고 답한 것만으로 끝내지는 않았습니다. 사진을 제대로 읽는지, 화면이 꺼져도 공부 시간이 이어지는지, 다른 계정의 기록이 보이지 않는지처럼 실제 사용 상황을 기준으로 결과를 확인했습니다.

## 1 서비스의 목적에 맞춰 AI의 제안을 판단했습니다

자연어로 앱 제작을 요청하면 초안을 얻을 수 있지만, 그 결과가 제가 원하는 서비스인지는 별도로 판단해야 했습니다. 저도 처음에는 API 사용법이나 서버 실행 방법을 묻고 따라가는 단계였습니다. 이후에는 필요한 기능을 말하는 데서 더 나아가, 어떤 상황에서 어떻게 작동해야 하는지 정하고 결과를 확인하게 됐습니다.

AI와 논의하면서 아이디어가 확장되기도 했고, 제가 처음 생각한 방식을 바꾸기도 했습니다. Timora의 저장 간격을 정할 때는 자주 저장할수록 좋다고 생각했지만, 데이터가 지나치게 늘어난다는 설명을 듣고 구조를 수정했습니다. 반대로 여러 기기에서 타이머를 쓸 때는 새 기기를 막자는 AI의 권장안을 받아들이지 않고 같은 계정의 상태가 이어지도록 요구했습니다.

기술적인 해결 방법까지 모두 제가 먼저 제시한 것은 아닙니다. 저는 필요한 동작과 문제를 정했고, AI가 구현 방법을 제안하거나 코드를 수정했습니다. 그 설명을 이해하고 실제 사용 목적에 맞는지 판단한 뒤 다음 요구를 정했습니다. 개발 과정에서 제 역할은 결과를 요청하는 데서, 제안과 결과를 비교하며 방향을 결정하는 쪽으로 넓어졌습니다.

## 2 KITA의 목표를 자체 AI에서 시험 학습으로 구체화했습니다

### 2.1 무엇을 만드는 것보다 어떤 문제를 해결할지 정했습니다

처음에는 외부 AI를 연결하지 않고 수학·과학 공부를 도와주는 AI 자체를 만들고 싶었습니다. ChatGPT와 대화하며 학습 데이터를 모으고 정제하는 과정부터 모델 학습과 평가, 잘못된 답변을 줄이는 방법까지 살펴봤습니다.

모델을 학습시키는 데는 데이터뿐 아니라 GPU와 서버 운영비가 필요했고, 로그인과 데이터 저장, 보안·개인정보·저작권도 고려해야 했습니다. 필요한 조건을 검토한 뒤 실제로는 Ollama와 Qwen2.5 계열 로컬 모델을 연결해 외부 API 없이 이차함수 문제의 답변이 생성되는 것을 확인했습니다. 대규모 모델을 직접 학습시킨 단계는 아니었습니다.

이 과정을 거치며 제가 해결하고 싶은 문제는 범용 모델을 만드는 것 자체보다 학생의 시험 성적을 높이는 데 있다는 쪽으로 방향이 구체화됐습니다. 같은 정답이라도 시험장에서 오래 걸리거나 계산 실수가 많으면 학생에게 충분히 도움이 되지 않는다고 봤습니다. 그래서 풀이를 제공하는 기능과 풀이 과정·시간·오답을 살피는 기능을 연결하려고 했습니다.

### 2.2 정답 이후의 학습을 기능으로 나눴습니다

“문제를 맞히는 AI가 아니라 시험 점수를 실제로 올려 주는 AI.” 이 목표에 맞춰 기본·단계별 해설과 정답 설명뿐 아니라 오답 이유, 빠른 풀이·가장 짧은 풀이·암산·시험장 풀이·정석·직관·상위권 접근을 비교하도록 방향을 정했습니다. 답을 주는 것과 실제 점수가 향상됐다는 것은 구분하며, 성적 향상 효과를 검증한 단계는 아닙니다.

| 제가 넓힌 학습 범위 | 기능으로 구체화한 내용 |
|---|---|
| 문제와 풀이를 이해하기 | 유형·난이도·출제 의도·킬러 여부를 살피고, 계산과 불필요한 과정을 줄이는 풀이를 비교합니다. |
| 학생의 풀이를 살피기 | 실력·약점·반복 오답·계산 실수·풀이 시간을 분석하고 사용자 풀이 평가와 더 빠른 방법 추천, 상위권 풀이 데이터 활용을 연결합니다. |
| 혼자 풀 수 있도록 돕기 | AI 티칭·힌트·단계별 유도·수준별 설명·질문 기능, 오답노트·복습·개념 압축을 연결합니다. |
| 실전에 맞춰 학습하기 | 실전 시험 모드·시간 배분·속도 최적화·전략 추천·실수 감지, 유사 문제·난이도 변형·예상 문제·오늘의 문제 추천을 구상했습니다. |
| 학습을 이어가기 | 학습 경로·성장 추적·장기 기억·장기 약점·학습 스타일·멘탈 및 행동 분석, 경쟁·랭킹을 장기 방향으로 정했습니다. |

이 로드맵을 한꺼번에 구현하기보다는 기본·빠른 풀이와 학생 분석, 사진 입력부터 연결했습니다. 일부 기능은 실행해 확인했지만 전체 추천 기능과 충분한 상위권 풀이 데이터 축적은 아직 남아 있습니다. 기능 수를 늘리는 것과 제가 정한 학습 목표를 달성하는 것도 같은 것으로 보지 않았습니다.

## 3 KITA에서 오류 수정의 기준을 다시 정했습니다

### 3.1 오류 문구가 바뀌어도 사진 인식은 해결되지 않았습니다

사진 풀이를 실행했을 때 인식률이 낮거나 IMAGE_TYPE_NOT_ALLOWED 오류가 나타났습니다. 사진을 문제풀이보다 그래프 분석으로 먼저 분류하거나, Study AI의 502 HTML 오류가 답변창에 그대로 나오는 문제도 있었습니다. 저는 실제 휴대폰 화면에서 확인한 문제를 전달했습니다.

Codex는 업로드 형식과 분류 순서를 바꾸고, 오류가 사람이 읽을 수 있는 문구로 표시되도록 수정했습니다. 이후 압축과 fallback도 추가했습니다. 그러나 오류 표시가 정리된 뒤에도 사진 분석이 기대에 미치지 못해, 저는 인식 품질 자체를 다시 문제로 제기했습니다.

제가 다시 요구한 것은 오류창을 없애는 것이 아니라 문제 사진을 제대로 읽는 것이었습니다. Codex는 원본·회색조·대비·확대·선명화·고대비·이진화·반전 등 전처리와 여러 OCR 후보 비교, O/0·I/l/1 및 수식 표기 보정, 외부 비전 AI 보조 경로로 구현을 넓혔습니다. 이 기술적 구현은 AI가 담당했으며, 저는 실제 결과를 보고 개선이 필요한 기준을 다시 제시했습니다.

수정 후 Codex는 공개 서버에서 3x+2=11 이미지의 답을 x=3으로 풀이하는 시험에 성공했다고 보고했습니다. 저는 실제 화면에서 발견한 인식 문제를 바탕으로 수정 범위를 넓혔고, 코드 구현과 해당 서버 시험은 Codex가 수행했습니다. 이 한 문제의 성공만으로 모든 사진을 정확히 읽는다고 판단하지는 않았습니다.

### 3.2 사용자가 먼저 분류해야 하는 입력 방식을 바꿨습니다

사진·그래프·도형을 별도 탭으로 나누면 사용자가 앱에 올리기 전에 사진의 종류부터 판단해야 했습니다. 저는 이 분류를 사용자에게 맡기기보다 앱이 처리하도록 바꿨습니다. 질문이나 문제를 따로 입력하지 않아도 사진 하나만 올리면 내용을 분석하고 그에 맞는 답변을 제공하도록 결정했습니다.

기본 풀이·빠른 풀이·상위권 접근·실수·복습을 구분하되, 일반 질문까지 문제풀이 틀에 넣는 답변은 바꾸도록 했습니다. r3·v02처럼 깨지는 수식과 줄바꿈·표현도 수정했습니다. 홈과 AI 화면을 분리하고 로그인 버튼을 복구했으며, 메뉴를 단순화하고 더보기로 정리했습니다. 객관식은 작은 표시만 누르는 대신 답안 박스 전체를 클릭할 수 있게 했습니다.

### 3.3 로그인 화면보다 실제 접근을 확인했습니다

로그인 화면이 있어도 링크로 들어가면 내부 기능이 보이는 문제가 있었습니다. 저는 미로그인 상태에서 어디까지 접근할 수 있는지를 기준으로 다시 수정하도록 했습니다.

관리자 코드 없이 관리자 화면이 보이던 문제도 같은 기준으로 확인했습니다. Codex가 보호 페이지 인증·관리자 인증·JWT·환경변수와 관리자 테스트 계정을 구현하고 수정했습니다. 기능의 화면이 있다는 설명에서 그치지 않고, 허용되지 않은 사용자가 실제로 들어갈 수 있는지를 확인하도록 범위를 넓혔습니다.

## 4 Timora의 타이머를 실제 공부 상황에 맞췄습니다

### 4.1 기존 코드의 완료 상태부터 다시 확인했습니다

Timora는 My Study App이라는 공부 타이머·플래너에서 출발했습니다. 열품타와 같은 타이머를 넘어 홈·노트·마인드맵·플래너·캘린더·입시 분석·AI 스터디 도우미·설정을 연결하고 싶었습니다. 그러나 기존 코드를 다시 확인했을 때 UI 골격과 기본 타이머만 있었고, 서버·로그인·영구저장은 없었습니다. 약 1,520줄이 main.dart에 집중돼 있었고 일부 기능은 더미였습니다.

저는 기존 코드가 있다는 이유로 완료됐다고 가정하지 않고, 각 기능이 실제로 작동하는지 처음부터 다시 확인하기로 했습니다. 이전 MyApp 클래스명을 참조하는 테스트 실패도 확인됐습니다. 화면을 더 추가하기 전에 모델·상태·서비스와 저장 구조부터 연결하도록 순서를 정했습니다.

### 4.2 화면 잠금과 앱 이탈을 다른 행동으로 봤습니다

공부 중 화면이 꺼지는 것과 다른 앱으로 이동하는 것은 의미가 달랐습니다. 전자는 휴대폰을 내려놓고 공부하는 상황에서도 생기지만, 후자는 공부 앱을 벗어나는 행동입니다. AI의 초기 lifecycle 처리가 두 상태를 충분히 구분하지 못하자 동작 기준을 다시 정했습니다.

| 사용 상황 | 제가 정한 동작 |
|---|---|
| 앱 내부의 탭 이동 | 계속 측정합니다. |
| 화면 꺼짐과 잠금 | 계속 측정합니다. |
| 다른 앱으로 이동 | 측정을 중지합니다. |
| Android 뒤로가기 | 시간이 멈춘다는 경고를 보여 주고 앱에 남을 기회를 줍니다. |

제가 정한 것은 상황별 동작이었고, Flutter lifecycle에 Android Kotlin과 MethodChannel을 연결하는 실제 구현은 Codex가 맡았습니다. 모든 Android 환경을 검증한 것은 아니지만, 타이머를 단순히 시작·정지하는 기능에서 사용자의 행동을 구분하는 기능으로 바꿨습니다.

### 4.3 두 번째 기기를 막는 권장안을 바꿨습니다

같은 계정으로 여러 기기를 사용할 때 Codex는 새 기기의 시작을 막는 방식을 권장했습니다. 하지만 저는 같은 계정으로 접속했다면 기기마다 별개의 타이머가 생기는 것이 아니라, 진행하던 공부 상태가 이어져야 한다고 봤습니다. 다른 기기에 접속해도 기존 타이머를 이어 쓰는 방식으로 바꾸기로 했습니다.

Codex는 active_timers와 JSONB, Supabase Realtime으로 같은 계정의 타이머 상태를 공유하도록 구현했습니다. 두 화면에서 시작·일시정지 상태가 동기화되는 것을 확인했습니다. 중복 실행을 막는 데서 끝내지 않고, 제가 원한 계정 단위의 연속 사용으로 요구사항을 바꾼 과정입니다.

## 5 공부 기록의 기준과 저장 방식을 다시 선택했습니다

### 5.1 자정 이후 공부까지 하나의 학습일로 봤습니다

자정이 지났다는 이유만으로 공부 기록이 바로 나뉘지 않도록 학습일 경계를 오전 6시로 정했습니다. 단순 초기화만 요청하지 않고, 실행 중인지 정지 상태인지에 따라 다음 동작도 나눴습니다.

측정 중 오전 6시가 되면 이전 학습일 기록을 마감하고 새 학습일 측정을 이어가며, 정지 상태라면 기록을 마감한 뒤에도 정지 상태를 유지하도록 했습니다. 앱이 꺼져 있으면 다음 실행 때 경계를 처리하도록 구현했습니다. 코드 반영과 모든 상황의 실제 오전 6시 검증은 구분하며, 전체 실사용 조건의 검증은 남아 있습니다.

### 5.2 자주 저장하는 방식의 문제를 이해하고 바꿨습니다

처음에는 30초마다 저장하면 기록을 안전하게 남길 수 있다고 생각했습니다. 그러나 매번 새 데이터 행이 생기면 저장량과 조회 부담이 커진다는 설명을 듣고 방식을 바꿨습니다. 화면 갱신과 시간 누적, 최종 저장을 나누고 완료된 1시간 단위 반영과 오전 6시 마감을 연결했습니다.

Reset과 Session Save를 제거하고, 과목을 바꿔도 이전 과목의 누적시간을 보존하도록 했습니다. 서버 전송에 실패하면 로컬 대기열에 남겼다가 재연결 시 보내고, UUID와 upsert로 중복 생성을 방지하도록 구현했습니다. 처음 생각한 저장 빈도를 고집하지 않고 기록 보존과 서버 부담을 함께 고려하게 됐습니다.

### 5.3 저장 위치를 선택한 뒤 실제 계정 격리까지 확인했습니다

Codex는 기기에만 저장하는 방식과 로그인 계정으로 서버에 저장하는 방식을 제시했습니다. 저는 공부 기록이 특정 기기에 묶이지 않고 계정을 따라 이어져야 한다고 판단해 서버 저장을 선택했습니다. 동시에 계정마다 데이터가 분리돼야 한다는 보안 기준을 함께 정했습니다.

Supabase의 Auth·PostgreSQL·사용자 UUID·RLS로 목표·할 일·공부 세션·캘린더·목표시간을 저장하도록 구현했습니다. Publishable key와 서버 전용 Secret key·service_role의 차이도 설명을 들으며 구분했습니다. 가입 후 할 일 체크와 타이머 표시가 바로 갱신되지 않는 문제를 발견했고, 서버 저장과 화면 갱신이 다르다는 설명을 들은 뒤 수정 결과를 다시 확인했습니다.

추가·조회·수정·삭제와 재로그인 후 복원을 확인하고, AI의 안내에 따라 실제 두 계정을 만들어 서로의 기록이 보이지 않는지 양방향으로 점검했습니다. 제가 RLS를 처음부터 알고 구현한 것은 아니지만, 보안 코드가 있다는 설명을 실제 사용 결과로 확인했습니다.

## 6 Timora의 계획 화면과 가입 흐름을 서비스로 연결했습니다

### 6.1 플래너의 두 형식을 결합했습니다

시간표형과 To-do형 중 하나만 선택하는 대신 할 일에 선택적으로 시간대를 붙이는 하이브리드 방식을 택했습니다. 과목·예상 시간·시작과 종료 시각, 날짜별 계획과 완료율, 계획에서 타이머 시작을 연결하도록 했습니다. 할 일 중심으로도 쓸 수 있고 필요한 경우 시간 계획까지 세울 수 있게 한 것입니다.

노트 탭을 없애서 플래너로 바꾸기보다 별도로 추가했습니다. 홈은 오늘의 목표와 할 일 요약, 플래너는 계획 편집, 캘린더는 날짜별 조회를 맡도록 같은 todo 데이터를 공유하게 했습니다. 일·주·월 통계, 반복 계획·이월·순서 변경 등 장기 기능 전체와 최종 migration의 운영 DB 반영까지 완료된 것으로 보지는 않았습니다.

### 6.2 이메일이 실제 다른 사용자에게 가는지 확인했습니다

두 번째 계정을 시험하는 과정에서 email rate limit exceeded가 발생했습니다. Supabase 기본 이메일의 제한을 설명받고 Resend Custom SMTP를 연결했지만, 다른 이메일 주소에는 여전히 발송되지 않았습니다. 저는 표시된 발송 가능 횟수와 실제 수신자 제한이 같은 조건인지 다시 확인했습니다. 설정이 끝난 것보다 다른 사용자가 가입 이메일을 받을 수 있는지가 중요했습니다.

Resend 로그의 HTTP 403과 onboarding@resend.dev 테스트 도메인의 수신자 제한을 확인했습니다. 발송 횟수와 수신자 제한은 다른 조건이라는 설명을 듣고, 일반 사용자가 가입할 수 있도록 실제 도메인을 구매하는 방향으로 진행했습니다.

KITA와 별도 서비스라는 의도를 분명히 하고 이름 후보를 비교했습니다. AI는 Studimo를 우선 추천했지만 저는 Timora를 골랐습니다. Cloudflare Registrar에서 timorastudy.com을 실제 구매했고, 한글 주소 입력 오류는 영문 주소로 수정했습니다. Resend에 도메인을 추가한 뒤 Cloudflare DNS의 MX·SPF·DKIM을 설정하고 Verified를 확인해 noreply@timorastudy.com으로 발신자를 바꿨습니다.

Flutter Web을 별도의 Timora Firebase 프로젝트에 배포해 timora-study.web.app에서 HTTPS 공개 테스트를 진행했습니다. 도메인 구매와 메일 인증까지 진행한 것과 앱의 사용자 정의 도메인·인증 redirect가 전체 흐름에서 검증된 것은 구분합니다. 처음에는 도메인과 배포 서비스의 차이도 질문했지만, 실제 가입 문제를 해결하면서 각각의 역할을 이해하게 됐습니다.

## 7 Jarvis에서 명령의 목적을 기준으로 다시 분류했습니다

Jarvis는 여러 AI와 컴퓨터 기능을 하나로 연결하는 개인비서로 만들었습니다. 일반 답변은 ChatGPT, 긴 글·보고서는 Claude, 개발 작업은 Codex, 앱 실행은 Automation, 기억은 Memory, 확장은 Plugin으로 나눴습니다. 실제 Python 코드와 여러 파일의 구현·수정은 주로 Codex가 담당했습니다.

### 7.1 주식 조회와 실제 거래를 나눴습니다

초기 안전 로직은 주식이라는 단어가 포함됐다는 이유로 삼성전자 주식 정보를 보는 화면을 여는 작업까지 막았습니다. 돈이나 계정 상태를 바꾸는 행위를 제한하려던 기준이 정상적인 정보 조회에도 적용된 것입니다.

저는 조회·검색·시세·차트와 매수·매도·주문·결제를 구분해야 한다고 판단했습니다. 정상 조회는 허용하고 실제 금전 실행은 계속 제한하도록 수정했습니다. 위험한 작업을 차단하는 기능이 있다는 것보다, 무엇을 허용하고 무엇을 막아야 하는지 사용 목적에 맞춰 다시 나눈 과정이었습니다.

### 7.2 같은 open 명령도 의도에 따라 처리하게 했습니다

브라우저 기능을 추가한 뒤 메모장을 여는 작업까지 브라우저 명령으로 분류되는 테스트 실패가 생겼습니다. 프로그램을 여는 것과 웹페이지를 여는 것을 구분하지 않고 같은 동사만으로 판단한 것이 원인이었습니다. Chrome·browser·검색·주가·시세처럼 브라우저 의도가 드러날 때만 해당 모듈을 쓰도록 기준을 바꿨습니다.

사용 방식도 바꿨습니다. 웹 UI보다 독립된 프로그램이 목적에 맞다고 판단해 Tkinter 네이티브 화면으로 변경했고, 중앙 HUD와 마이크·명령 로그·상태 패널을 조정했습니다. WAKE 버튼을 매번 누르는 대신 실행 시 자비스·jarvis·쟈비스 호출어를 자동으로 기다리도록 했습니다.

Codex는 SpeechRecognition·PyAudio·pyttsx3를 연결하고, 메모장·계산기·VS Code·탐색기·터미널 실행, 위험한 삭제 차단, Memory 저장·검색·삭제와 로그를 구현했습니다. PyInstaller 실행 파일의 \_MEI... 경로에서 FileNotFoundError가 발생하자 설정 저장을 AppData\\Roaming\\Jarvis\\settings.json으로 옮겼습니다. 테스트는 23·29·34·38개 통과 기록까지 늘었지만, 음성 오인식이나 모든 기능의 완전 자동 통합까지 해결된 것은 아닙니다.

## 8 공개 사용과 유료 운영을 위해 준비했습니다

KITA는 로컬 실행에서 Cloudflare Tunnel을 통한 공개 접속으로 옮겼지만, 노트북이 켜져 있어야 하고 임시 URL에 의존하는 문제가 있었습니다. 이후 GitHub·Render·Firebase Hosting으로 서버와 화면을 공개하는 방향으로 진행했습니다. 메인 서버와 Study AI 서버를 나누며 CORS·502·JWT_SECRET must be at least 48 characters 같은 오류도 해결해야 했습니다.

처음 FastAPI의 /solve를 시험할 때는 Swagger의 Try it out·입력 JSON·Execute·Cancel도 하나씩 확인했습니다. 사용자 ID·과목·수준·풀이 시간·정답 여부를 보내 HTTP 200과 분석 결과를 확인했고, 과학으로 범위를 넓혔습니다. WinError 10048 포트 충돌과 PowerShell 출력을 명령으로 혼동한 일도 겪었습니다.

이후에는 HTML/CSS/JavaScript 화면, Node.js/Express 메인 서버, Python/FastAPI, MongoDB Atlas, Firebase의 역할과 JSON·FormData 전달을 구분하며 요구를 구체화했습니다.

요금제는 무료와 월 5천 원·1만 원·1만5천 원 수준을 검토했습니다. 단순 호출량보다 풀이 수준과 접근 방식에 차이를 두려 했고, 친구 초대·포인트·풀이 공유·주간 랭킹·관리자 문제집·답지 업로드도 서비스 구조에 포함했습니다. Toss Payments와 사업자 등록·정산계좌·PG 계약을 검토했으나 실결제를 켜지는 않았습니다.

정식 유료 상용화는 아직 시작하지 못했습니다. 학생으로서 학업·대회·다른 프로젝트를 병행하면서 사업자 등록과 결제 행정절차에 충분한 시간을 확보하지 못했습니다. 개발과 공개 테스트를 진행하고 실제 도메인까지 구매했지만, 결제 절차와 일부 기술적 최종 검증이 남아 있어 현재는 유료 기능을 준비하는 단계입니다.

저는 모든 코드를 직접 작성하지 않았습니다. 필요한 기능과 우선순위, 화면 흐름, 기록의 기준, 보안 요구, 서비스화 방향을 정했고, AI가 제시한 구현을 실제 사용과 비교했습니다. 잘 모르는 기술은 질문하며 이해했고, 설명을 듣고 제 생각을 바꾸기도 했습니다. 반대로 제 서비스에 맞지 않는 권장안은 받아들이지 않고 동작 기준을 다시 정했습니다.

### 9.1 프로젝트별 확인 범위

| 프로젝트 | 실제 확인하거나 진행한 내용 | 아직 남아 있는 내용 |
|---|---|---|
| KITA | API·기본/빠른 풀이·학생 분석·일부 OCR, 인증 수정과 서버·공개 배포를 진행했습니다. | 전체 학습 로드맵·모든 OCR 상황·성적 향상 효과·실결제와 유료 운영, 카카오 로그인·앱스토어 패키징·약관과 개인정보처리방침·전용 도메인의 전체 완료는 남아 있습니다. |
| Timora | 가입·로그인·서버 저장·재로그인 복원·CRUD·두 계정 격리·일부 다중기기 동기화·SMTP·도메인 인증·공개 배포를 확인했습니다. | 모든 오전 6시 상황과 Android 환경, 플래너 최종 migration, 사용자 정의 도메인과 인증 redirect의 전체 흐름, 장기 기능의 검증이 남아 있습니다. 노트 편집·AI 스터디 도우미의 UI 뼈대, 입시 분석의 다음 액션과 알림의 더미 기능도 남아 있습니다. |
| Jarvis | 실제 AI 응답·라우팅, 로컬 자동화·음성·Memory·일부 안전 기능과 테스트, 설정 저장 경로 수정을 진행했습니다. | 독립 API 기반 Codex 자동 제어와 모든 기능의 완전 자동 통합, 전체 음성 환경·안전성 검증이 남아 있습니다. |

개발을 거듭하면서 제가 내리는 결정은 더 구체적이 됐습니다. KITA에서는 사진을 올리는 방법과 인식 품질을, Timora에서는 화면 잠금·기기 이동·학습일 경계와 저장 실패를, Jarvis에서는 같은 단어가 포함돼도 목적이 다른 명령을 구분했습니다. AI와 대화하며 이해한 내용을 실제 서비스의 조건으로 바꾸고, 실행 결과가 그 조건을 만족하는지 확인하며 개발을 이어갔습니다.
